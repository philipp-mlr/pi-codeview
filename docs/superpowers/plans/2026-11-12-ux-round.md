**Decisions (approved by Philipp 2026-11-12, "yes sounds great"; scope "everything listed", marks "clearly different"):**
- Floating editor for `pa`, `pn`, `pe`: about 80 columns, wraps, `filetype=markdown`, starts in insert mode; the title says where the text goes, e.g. ` pi ask · session.lua:5 · refactor-discover `. `<C-s>` sends in insert and normal mode, `<CR>` sends in normal mode, `q`/`<Esc>` in normal mode cancels. `pe` prefills the current text. Sending empty text cancels.
- New key `<leader>pk` "peek" (`:PiPeek`): in a checkpoint diff shows the full note and the file's why in a wrapping float; on an annotated line shows the full annotation. Not `K` (that is LSP hover).
- Previews: the note line in the diff shows the first 80 characters then `… <pk>`; annotations show at most 2 wrapped lines then `…`.
- Checkpoint list: `signcolumn=no`, `foldcolumn=0`, `cursorline`; width `max(40, min(60, 35% of columns))`; details wrap to the text width; help line `<CR> open · za more · g? keys`; `g?` shows all keys. Still opens on its own when a checkpoint arrives; `setup({ panel = { auto_open = false } })` turns that off.
- Live marks: `▎` instead of `┃`, `Added`/`Changed`/`Removed` colours; the whole-line highlight is off by default.
- Session picker: named and checkpoint-mode sessions first, rows `name · worktree · state · 5m ago`, no repeated root. "Ago" needs an additive `lastActive` (epoch ms) in the `status` result.
- `pc` with no remarks still continues without asking (approved last round).

## Global Constraints

- nvim 0.12 API; Philipp's setup: nowrap, `signcolumn=yes:1`, gitsigns, LSP, lualine, diffview.nvim, which-key may or may not be installed — never require it.
- Protocol stays version 2; additions only. Default keys never replace existing mappings. All keys under `<leader>p`.
- Every user-visible key hint goes through `keys.label(name, ":Command")`.
- No Nerd Font glyphs; only plain Unicode (`▎ ● ✓ ✗ · … ✎ ⏸`).
- Highlight groups are linked with `default = true` in `highlights.lua` so colourschemes and users can override them; colour never carries meaning alone.
- Each task: TDD (nvim specs in `nvim/tests/*_spec.lua`, vitest in `test/`), README updated where behaviour changes. All three suites green before commit: `npm test`, `npm run typecheck`, `nvim --headless -l nvim/tests/run.lua > /tmp/out 2>&1; echo exit=$?` (check the runner's exit code and that /tmp/out has no FAIL).
- Commits conventional, signed; never `git add -f` under `.superpowers`.

## Review Focus

1. Floating editor: no lost text (closing the window by `:q`, `<C-w>c`, or leaving it cancels cleanly, no stray buffers); works when invoked from a diff tab, the panel, a visual selection.
2. Everything fits at 80, 120 and 200 columns with `signcolumn=yes:1`; nothing writes past the window edge.
3. Session naming in sends is right when the buffer's worktree differs from the attached one.
4. Old extensions without `lastActive` still work in the picker.

### Task 7: No dead ends when nobody can review

From a real session (2026-11-12): a pi-subagents worker in another bc-apps worktree loaded pi-nvim, read the repo-wide `pi-nvim.checkpoints = true`, passed the 150-line cap, and every editing tool was blocked with "Call checkpoint with a note first". The worker has no `checkpoint` tool and no Neovim review, so it stopped.

Root cause: (1) the mode is repo-wide git config (stays that way, Philipp's ruling); (2) every pi session, subagent children included, starts in checkpoint mode — `otherReviewSession()` only looks at the same root; (3) `capBlock()` never checks that this session can call `checkpoint` at all.

**Files:** `extensions/loop.ts`, `extensions/pi-nvim.ts`, `extensions/server.ts` (count attached clients), new `extensions/open-nvim.ts`, `docs/protocol.md`, `test/extension.test.ts`, `test/e2e.nvim.test.ts`; `nvim/lua/pi/init.lua` / `session.lua` (`require("pi").review(root, session_id)`), `nvim/doc/pi.txt`, README.

- [ ] **A — never block without a way out.** Checkpoint mode only takes effect in a session that can be reviewed: `ctx.hasUI` is true AND `checkpoint` is among `pi.getActiveTools()` (checked when it matters — cap block, `checkpoint()`, end of run — not only at start, since a child runtime may apply its tool allowlist after `session_start`). Otherwise the session behaves exactly like mode off: no cap block, no chunk at end of run, no waiting. `describe()` / status say why (`checkpoint mode is on for this repo, but this session can't stop for review`). The status `mode` field reports the effective mode. Tests: tool not active → no cap block past the cap, no chunk at end of run; hasUI false → same; tool active + UI → unchanged.
- [ ] **B — tell Philipp when nobody can review, offer to open it in Neovim.** When a checkpoint opens and no Neovim client is attached to this session's socket: pi notifies `pi: checkpoint N waiting — no Neovim attached` and asks with `ctx.ui.confirm` "Open checkpoint N in Neovim?" (non-blocking for other work; the tool is waiting anyway). Yes →
  1. **Running nvim in this worktree:** for each live `$XDG_RUNTIME_DIR/nvim.*` socket (also `$NVIM` if set), `nvim --server <sock> --remote-expr` with a 2 s timeout asks `luaeval('require("pi").review(<root>, <sessionId>)')`. pi.nvim's `review()` returns `"ok"` only when that nvim's cwd (or current buffer) is inside `root`, then attaches to exactly that session and opens the checkpoint list. First `"ok"` wins; stale sockets fail fast and are skipped.
  2. **Else, inside herdr** (`HERDR_PANE_ID` set and `herdr` on PATH): split a pane to the right of pi's pane with cwd `root` and start `nvim -c "lua require('pi').review(<root>, <sessionId>)"`. Read `herdr pane split --help` / `herdr pane run --help` for the exact calls.
  3. **Else:** notify `pi: open Neovim in <root> and press <pv>` (with `:PiCheckpoints` as the command).
  No → notify `pi: checkpoint N waits — review it in Neovim or run /checkpoints continue <note>`. Never ask again for the same checkpoint. No prompt at all when a client is attached.
  Tests: no client → notify + confirm called; client attached → neither; yes with a fake nvim socket answering "ok" → that path used; no nvim, herdr env set → herdr command built (stub execFile); neither → the command hint. nvim spec for `review()` (wrong root → "not here", right root → attaches to that session id and opens the panel).
- [ ] README + vimdoc: subagents and other sessions without the checkpoint tool or a UI never stop for review; what happens when no Neovim is attached. Commit `fix: checkpoint mode never blocks a session nobody can review` (and a second `feat: open a waiting checkpoint in Neovim from pi` if clearer).

### Task 8: Open a checkpoint in Neovim without herdr

Philipp (2026-11-12): keep it tool-agnostic with one setting, plus built-in defaults for herdr, tmux and zellij.

**Files:** `extensions/open-nvim.ts`, `extensions/git.ts` (read `pi-nvim.openCommand`), `extensions/loop.ts` (pass config, notice per opener), `test/extension.test.ts` (or a new `test/open-nvim.test.ts`), `docs/protocol.md` if it documents the open flow, README, `nvim/doc/pi.txt`.

Order when no running nvim in the worktree answers `review()`:
1. **`git config pi-nvim.openCommand`** (read like the other `pi-nvim.*` keys; repo or global): a command line split into arguments on whitespace (no shell), with `{root}` and `{session}` replaced inside arguments, and `{nvim}` replaced by the three arguments `nvim -c "lua require('pi').review(vim.env.PI_NVIM_ROOT, vim.env.PI_NVIM_SESSION)"` passed as separate argv entries (`nvim`, `-c`, `lua require(...)`). It runs with `PI_NVIM_ROOT` and `PI_NVIM_SESSION` in its environment and cwd = root. Exit code 0 = opened. Example in docs: `wezterm cli split-pane --right --cwd {root} -- {nvim}`, `kitty @ launch --location=vsplit --cwd {root} {nvim}`. If it fails, notify `pi: pi-nvim.openCommand failed (exit N)` and fall through to the hint, not to the built-ins.
2. **herdr** when `HERDR_PANE_ID` is set (as today).
3. **tmux** when `TMUX` is set: `tmux split-window -h -c <root> -e PI_NVIM_ROOT=<root> -e PI_NVIM_SESSION=<id> [-t $TMUX_PANE] nvim -c "lua require('pi').review(vim.env.PI_NVIM_ROOT, vim.env.PI_NVIM_SESSION)"` — one execFile call, the nvim command as separate argv entries (tmux joins and runs them via its default shell; verify with tmux 3.8 that the -c lua argument survives — if tmux passes it through a shell, keep the fixed command free of shell-special characters, as it already is).
4. **zellij** when `ZELLIJ` is set: `zellij run --direction right --cwd <root> -- env PI_NVIM_ROOT=<root> PI_NVIM_SESSION=<id> nvim -c "lua …"` (env via `env`, since `zellij run` has no env flag; check `zellij run --help` semantics from the docs, zellij is not installed here — stub-tested only).
5. Else the hint (unchanged): `pi: open Neovim in <root> and run :PiCheckpoints (default <leader>pv)`.

`OpenedIn` becomes `"nvim" | "pane" | "command" | "hint"` with the tool name for the notice: `pi: checkpoint N opens in a new Neovim pane (tmux)`.
